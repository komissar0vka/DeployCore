## Каталог и изменения

- Backend: `package_api.py`, `package_models.py`, `package_schemas.py`, `package_storage.py`; регистрация роутера в `main.py`. Миграция `0003_package_catalog` добавляет `software_packages`, `software_versions`, `package_detection_rules`, `package_artifacts`. Существующие таблицы сохраняются.
- Frontend: `packages.tsx`, интеграция с навигацией, счётчиком дашборда, API-клиентом и общими сообщениями.
- Инфраструктура: версия образа сервера с `msitools` и `osslsigncode`, выделенный Docker-том `package-data`, потоковый маршрут Nginx. Изменены соответствующие Dockerfile, Compose, конфигурация Nginx и образец окружения.
- Контракт и проверки: `packages/api-contract/openapi.json`, `deploy/scripts/package_smoke.py` и подключение к существующим изолированным проверкам.

### API

- `GET, POST /api/v1/packages` — выборка с поиском/пагинацией и создание.
- `GET, PATCH, DELETE /api/v1/packages/{id}` — пакет с версиями, изменение сведений и логическая архивация.
- `POST /api/v1/packages/{id}/versions` — новая неизменяемая версия для архитектуры x64/x86.
- `PUT /api/v1/packages/{id}/versions/{version_id}/artifact?filename=...` — бинарный поток `application/octet-stream`.
- `GET /api/v1/packages/{id}/versions/{version_id}/artifact` — выдача файла как вложения и заголовок SHA-256.
- `POST /api/v1/packages/{id}/versions/{version_id}/approve` — подтверждение администратором после проверки.

Метаданные доступны всем вошедшим ролям. Создание, изменение, архивация, загрузка, скачивание и утверждение доступны Administrator и Super Admin. Изменения проверяют Origin и CSRF и записываются в аудит.

### Хранилище и эксплуатация

- `DEPLOYCORE_PACKAGE_MAX_MIB` по умолчанию 1024, верхняя граница 2048. `DEPLOYCORE_PACKAGE_RESERVE_MIB` по умолчанию 256. Загрузки сериализуются на томе. Ограничения размера и резерва проверяются до записи и во время передачи.
- Путь выбирается сервером по UUID версии. Артефакт неизменяем после первой успешной записи. Архивация скрывает продукт, сохраняя файлы и историю. При аварии незарегистрированный итоговый файл недоступен по API и заменяется при повторной загрузке той же версии.
- Для Authenticode используется локальный OpenSSL trust bundle. Чтобы доверять внутреннему центру подписи, подключите его PEM к контейнеру `server` через read-only bind mount в Compose override и установите `DEPLOYCORE_PACKAGE_CA_FILE` в путь внутри контейнера. Установка и соединения агентов используют свой действующий TLS-конфиг. Офлайн-проверка подписи и доверенной цепочки не заменяет антивирус и проверку отзыва с доступом к PKI.
- Неподписанный, повреждённый или недоверенный по Authenticode файл остаётся черновиком, если подходит по формату и архитектуре. Утверждение требует статуса `verified`. Для повторной проверки после изменения CA создаётся новая версия. Обновление политик для уже утверждённых пакетов и проверка хеша перед запуском относятся к будущему этапу.
- Для согласованного бэкапа остановите запись каталога и сохраните PostgreSQL и том `package-data` в одной точке. Хранилище и БД из разных снимков могут расходиться. Этот этап не вводит автоматический сборщик архивов.

### Запуск проверки

Из корня проекта выполните `deploy/scripts/smoke.sh`. Он поднимает отдельный Compose-проект с временной БД, искусственным CA для проверки подписи и отдельным томом установщиков. Рабочая миграция не запускалась. Windows Agent на этом этапе не менялся.

### Результаты проверки

- 17 тестов pytest, сборка TypeScript/Vite и Chromium прошли. Chromium проверил создание и редактирование программы, версию и аргументы, бинарную загрузку, кнопку утверждения, архивирование и мобильный режим Viewer на тестовых ответах API.
- Сквозной Compose прошёл с миграцией `0002_devices → 0003_package_catalog`, проверкой сохранения существующей записи, Alembic и OpenAPI. Проверены чтение и изменения по ролям, CSRF, MSI и EXE больше прежнего лимита API, SHA-256, x86/x64, ограничение размера, скачивание и запрет подмены. Оба формата были подписаны временным CA; изменённый после подписи EXE остался неутверждённым. Сохранность файлов и утверждения проверена после пересоздания API-контейнера.
- Прежние маршруты агентов прошли тесты регистрации, heartbeat, инвентаризации и восстановления. На Windows установщики не запускались. Очередь, протокол заданий и установка из каталога остаются следующими этапами. Рабочая панель и её база, FlipHunter и n8n остались без изменений.
