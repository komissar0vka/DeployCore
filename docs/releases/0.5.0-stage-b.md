# DeployCore 0.5.0 · этап B

## Объём

PostgreSQL хранит задания установки и удаления, отдельные цели, попытки доставки и историю. При создании требуется утверждённая версия с артефактом. Для удаления нужен разрешённый манифест удаления. Можно выбрать до 100 устройств с действующим ключом, в том числе офлайн. Панель показывает агрегированный прогресс обработки и события по каждой цели. Viewer читает очередь, Administrator и Super Admin создают и отменяют задания. Административные изменения проверяют Origin и CSRF и входят в аудит.

Миграция `0004_deployment_queue` добавляет `deployment_jobs`, `deployment_targets`, `deployment_attempts`, `deployment_events`. Частичный уникальный индекс исключает две активные цели на одном устройстве. Политика этапа B допускает только результаты `not_executed` и `cancelled`, поэтому дашборд и карточки не представляют транспортную проверку как установку.

## Протокол

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST | `/api/v1/deployments` | Создать задание с операцией, версией, устройствами и UUID `request_id` |
| GET | `/api/v1/deployments` | Выборка с пагинацией и числом активных заданий |
| GET | `/api/v1/deployments/{job_id}` | Прогресс, цели, попытки, состояние отмены и срок аренды |
| GET | `/api/v1/deployments/{job_id}/events?before={id}` | До 50 событий с курсором по ID |
| POST | `/api/v1/deployments/{job_id}/cancel` | Отмена ожидающих целей или запрос отмены подтверждённых |
| POST | `/api/v1/agent/{device_id}/jobs/poll` | Выдать подтверждённому агенту одну текущую доставку |
| POST | `/api/v1/agent/{device_id}/jobs/{target_id}/ack` | Подтвердить получение по `attempt_id` |
| POST | `/api/v1/agent/{device_id}/jobs/{target_id}/heartbeat` | Продлить аренду той же попытки и проверить запрос отмены |
| POST | `/api/v1/agent/{device_id}/jobs/{target_id}/result` | Сохранить терминальный результат по `attempt_id` |

- Повтор создания с тем же UUID тем же администратором возвращает исходное задание, если состав совпадает. Изменение версии, операции или множества устройств при том же UUID даёт 409.
- Машинные маршруты используют действующие HTTPS и Bearer-ключ конкретного устройства. Опрос по чистому журналу выдаёт наиболее старую ожидающую цель. Повторный poll до ACK получает тот же `attempt_id` в пределах 120-секундной аренды. После истечения создаётся следующая попытка, максимум пять. После исчерпания выдача отмечается как `failed`.
- Новый агент сохраняет попытку в защищённом DPAPI-журнале до ACK. ACK и heartbeat повторяемы. После ACK истечение аренды оставляет цель защищённой от повторной выдачи. Тот же агент восстанавливает срок по прежнему `attempt_id`. Если его локальный журнал потерян, задание остаётся заблокированным для восстановления оператором. Автоматическое выяснение исхода и админское разрешение потерянного журнала относятся к будущим этапам.
- Результат сохраняется на агенте до отправки, поэтому потерянный ответ можно повторить без нового события. Другой результат для закрытой попытки даёт 409. Отмена ожидающей выдачи действует сразу. После ACK сервер возвращает флаг отмены и ждёт ответа агента.
- Agent 0.3.3 понимает только ответ `mode=transport_only`. Он обменивается ACK, heartbeat и результатом. В ответе нет команд, аргументов или ссылок на установщик. При обращении к прежнему API 404 очереди не мешает heartbeat и инвентаризации. Ранее подключённые агенты продолжают прежний протокол; для очереди требуется новая сборка.
- Запуск MSI/EXE, скачивание установщика агентом и проверка установки относятся к этапу C. Перед добавлением исполнения потребуется протокол подтверждения результата на диске и политика разрешения случаев потерянного журнала.

## VPS

До разработки на корневом разделе было 4 692 099 072 свободных байта. После удаления временных тестовых копий и распакованного PowerShell стало 5 026 476 032 байта. Освобождено 334 376 960 байт. Проверены Docker и временные файлы; рабочих контейнеров, образов и постоянных томов очистка не касалась. Все миграции в этом этапе выполняются отдельным Compose-проектом с временными томами.

Для воспроизведения выполните `deploy/scripts/smoke.sh`, а для Go в `apps/agent` выполните `go test -race ./...`. Работающий экземпляр на VPS на этом этапе не обновлялся.

- Прошли 17 тестов Python, сборка TypeScript/Vite и Chromium. В браузере проверены выбор онлайн- и офлайн-устройств, создание, прогресс, история, отмена и права Viewer на мобильном экране.

Проверены Alembic, прежние агентские маршруты, RBAC, CSRF, восемь одновременных poll, повтор создания с двумя сессиями, истечение аренды до ACK, восстановление после ACK, повтор результата, отмена и перезапуск API.
- Прошли `go test -race ./...`, Windows `go vet` и кросс-сборка EXE/MSI. Go-тест моделирует ошибки ACK и отправки результата и восстановление по сохранённому журналу. На реальной Windows установщики не запускались.
- Нативный тест жизненного цикла MSI в `.github/workflows/deploycore-agent.yml` оставлен для ручного `workflow_dispatch`. Автоматический push запускает сборку и проверки без запуска установщика.
